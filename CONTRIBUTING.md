# Contributing to WebFlash

Thank you for helping improve the Sense360 firmware installer. This page covers how to file issues, how to open pull requests, and the local gate every change must pass.

## Filing issues

Use the issue templates on this repository:

- **Flash failure** for problems using the installer. Browser, browser version, and operating system are required fields because WebFlash depends on Web Serial, which only exists on desktop Chromium browsers.
- **Firmware request** to ask for a firmware build for a hardware configuration the installer does not currently offer.
- **Crash report** for installer crashes with a crash identifier.

For firmware behaviour after a successful flash, file on [sense360store/esphome-public](https://github.com/sense360store/esphome-public/issues) instead. For questions, use [Discussions on esphome-public](https://github.com/sense360store/esphome-public/discussions). See [SUPPORT.md](SUPPORT.md) for the full routing.

## Opening pull requests

- Develop on a feature branch and open the pull request against `main`. Never push to `main` directly.
- Keep the repository conventions: vanilla ES modules, no build step, no new third party runtime dependency beyond ESP Web Tools from the documented unpkg origin, desktop Chromium only.
- `manifest.json` and every `firmware-*.json` are generated by `scripts/gen-manifests.py`. Never hand edit them; regenerate and commit the diff together with the firmware change.
- Never weaken a blocking gate (provenance, release channel acknowledgement, signature and checksum verification, manifest freshness, service worker update). See [docs/standing-invariants.md](docs/standing-invariants.md) for the standing invariants that gate every PR, including the do not change guardrails for documentation only PRs.
- Fill in the pull request template, including the local gate statement.

## Local gate

Every pull request must pass this gate locally before it opens, and the output belongs in the PR body:

```bash
npm test
npm run validate:naming-policy
python3 scripts/gen-manifests.py --strict-validate --dry-run
npm run check:headers -- https://sense360store.github.io/WebFlash/
```

If the PR touches provenance, the manifest, or the install gate, also fill the reviewer checklist from the README into the PR body.

## Documentation conventions

- [docs/architecture.md](docs/architecture.md) is the canonical architecture narrative; update it, not `CLAUDE.md`, when the architecture changes.
- Historical records are archived and indexed in [docs/archive-index.md](docs/archive-index.md). Archived records are history; do not edit them.
- Customer facing copy must never contain internal engineering, task, or tracking identifiers, internal doc filenames, or internal script paths. Every unavailable customer option needs one plain language reason plus one suggested next step.
- PR bodies are plain prose: a summary, the key changes, the verify output, and an explicit statement of what stays gated. Do not use hyphens as sentence breakers. No emojis.
