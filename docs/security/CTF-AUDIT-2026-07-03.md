Read-only capture-the-flag audit. The auditor plays attacker against the owner's own
public repository and attempts to capture each flag using only non-destructive,
read-only means. A captured flag is a real vulnerability. No file in this repository
was edited, staged, committed, or deleted during the audit phase except this report.
No hard-stop file (publish/import workflow, `firmware/sources.json`, manifest, signing
key) was modified; no credential was rotated or printed in full.

(tracking `main` at `838a2d7`), read-only inspection of every workflow, the deployed
static Pages sources (`index.html`, `_headers`, `scripts/`), the install/flash path,

## Findings

### FLAG-SECRET-TREE — CAPTURED (contained) — Low

A real Ed25519 private key is committed:
`firmware-signing/keys/dev-2026-01-private.pem` (`-----BEGIN PRIVATE KEY-----` … redacted)
and its raw base64 twin `dev-2026-01-private.raw.b64`. It is a deliberately-exposed
test/CI fixture, correctly fenced, not a production credential:

- `firmware-signing/trusted-keys.json:26` pins `kid: dev-2026-01` with `"status":
  "test_only"` and a comment that the private half is committed on purpose and MUST NEVER
  be promoted to `active`.
- The verifier refuses `test_only` signatures in production mode
  (`trusted-keys.json:9` policy; `scripts/utils/firmware-signature.js`), and the fixtures
  it signs are "NOT installable from the deployed wizard."
- The production key `sense360-prod-2026-02` is `active` (`trusted-keys.json:18`) with only
  its public half committed; its private half is documented as living solely in the
  `WEBFLASH_FIRMWARE_PRIVATE_KEY_B64` Actions secret.

No `AKIA…`, `ghp_…`, `github_pat_…`, bearer token, or password was found in the tree or in
`git log -S 'BEGIN … PRIVATE'` history. Scored Low: a real private key is present (the flag's
capture condition), but it is a known, contained, verifier-fenced fixture. The only residual
is procedural — promotion of `dev-2026-01` to `active` would be catastrophic and is guarded
by a documented backstop test.

### FLAG-MANIFEST-TRUST — CAPTURED (documented design limit) — Low

The install path enforces client-side SHA-256 but does not enforce the cryptographic
signature that is present in the manifest.

- The deployed `manifest.json` carries, per build, a real Ed25519 signature under the
  active production key: `manifest.json:25-26`
  (`"signature_ed25519": …`, `"signature_key_id": "sense360-prod-2026-02"`).
- The wizard has a production-ready Ed25519 verifier
  (`scripts/utils/firmware-signature.js`) but does **not** enforce it: the
  `signature_verified` provenance check is a deliberate skip
  (`scripts/engine.js:33`; `scripts/utils/firmware-provenance.js:604,665`), consistent with
  the CLAUDE.md trust model that forbids claiming signature verification until it is a
  separate explicit project.
- SHA-256 **is** enforced as an install gate: `state.js` fetches each part
  `{cache:'no-store'}`, computes `crypto.subtle.digest('SHA-256', …)`, and compares against
  the manifest `part.sha256`, feeding the composite install gate. Residual subtlety: this
  gate runs over a parallel fetch, while the actual flash bytes are fetched and written by
  the upstream `<esp-web-install-button>` component (`install.js:363-365`); the hashed bytes
  and the flashed bytes come from independent fetches of the same HTTPS origin.

Net: integrity rests on HTTPS same-origin transport plus a SHA-256 UI gate; there is no
enforced end-to-end cryptographic chain from a trusted key to the flashed bytes, even though
a valid production signature is shipped. This is an intentional, documented posture, not a
regression. Scored Low: SHA-256 is gated and the transport anchor is TLS; exploiting the
parallel-fetch gap requires breaking TLS on the origin. Enforcing the already-present
Ed25519 signature would close it.

**Remediation (SEC-ED25519-ENFORCE-001, 2026-07-03):** the gated proposal below was
executed as the separate explicit project the code anticipated. `verifyFirmwareIntegrity`
(scripts/state.js) now runs Ed25519 verification of the downloaded bytes against the
pinned trust list in production mode alongside the unchanged SHA-256 check, and
`evaluateInstallGate` refuses install unless both verdicts pass (a verified-bytes result
with a missing or failed signature verdict fails closed). Before enforcement, every
deployed build (3 stable, 6 preview, 1 rescue, all signed by the active
`sense360-prod-2026-02` key) was proven to verify in production mode. The residual
parallel-fetch subtlety (gate hashes one fetch, esp-web-tools flashes another) is
unchanged and remains TLS-anchored.

### FLAG-SRI — CAPTURED — Low

- esp-web-tools (the security-relevant third-party script) **has** SRI: `index.html:63`
  loads `https://unpkg.com/esp-web-tools@10.2.1/dist/web/install-button.js?module` with
  `integrity="sha384-…"` and `crossorigin="anonymous"`, version-pinned. Its inline comment
  notes the hash covers the entry module only; the sub-chunks it dynamically imports from
  the whole-origin `unpkg.com` allowance are not SRI-covered.
- The Google Fonts stylesheet has **no** integrity: `index.html:33`
  `<link href="https://fonts.googleapis.com/css2?family=Inter…" rel="stylesheet">`. SRI is
  impractical for the Fonts CSS API (content varies by UA), so it is omitted; the residual
  injection surface is constrained by the `style-src`/`font-src` CSP allowlist.

Scored Low (hardening): the primary flash-driving script is SRI-pinned; the gaps are a
UA-varying stylesheet and unpkg sub-chunks.

### FLAG-DEP-VULN — CAPTURED — Low

`npm audit --package-lock-only` reports 6 advisories (3 high, 2 moderate, 1 low), all in the
Jest devDependency transitive tree (`ws`, `minimatch`, `picomatch`, `js-yaml`,
`brace-expansion`, `@babel/core`). `package.json` declares only `jest` and
`jest-environment-jsdom` as devDependencies with `"private": true` and no runtime
`dependencies`; the site ships zero runtime npm packages (only esp-web-tools from unpkg), so
none of these reach the browser. `.github/dependabot.yml` exists but covers only the
`github-actions` ecosystem, so these npm advisories are not auto-tracked. Scored Low
(CI/dev-only, no runtime exposure).

### FLAG-CSP — SECURE

GitHub Pages ignores `_headers`, so the enforced policy is the `index.html:15` meta tag:
`default-src 'self'; script-src 'self' https://unpkg.com; style-src 'self'
https://fonts.googleapis.com; font-src 'self' https://fonts.gstatic.com; connect-src 'self'
blob:; img-src 'self' data:; manifest-src 'self'; worker-src 'self' blob:; object-src 'none';
base-uri 'self'; form-action 'self'; upgrade-insecure-requests`. No `unsafe-inline` and no
`unsafe-eval` in `script-src` or `style-src`; `object-src 'none'` and `base-uri 'self'` are
both present. The flag's capture conditions (unsafe-inline / unsafe-eval / missing /
permissive) are not met. Hardening notes (not captures): `script-src` trusts the whole
`unpkg.com` origin (standard for esp-web-tools' transitive imports, partially mitigated by the
entry-module SRI), and `frame-ancestors`/`X-Frame-Options: DENY` from `_headers:33,36` are not
enforceable via meta tag on Pages, so clickjacking defense depends on a future
Netlify/Cloudflare migration.

### FLAG-SOURCES-INTEGRITY — SECURE

All 9 entries in `firmware/sources.json` carry a 64-hex `expected_sha256` pin (lines 13, 47,
81, 115, 142, 169, 203, 237, 264); none missing. The importer enforces two independent hash
checks in `scripts/import-firmware-sources.py`: `verify_sha256()` matches the downloaded
`.bin` against the upstream `checksums-sha256.txt` (raising if the line is absent), and
`assert_expected_sha256_matches()` additionally matches WebFlash's own pinned
`expected_sha256`, defeating a lock-step upstream swap of both asset and checksum. `block_tokens`
(default `FanTRIAC`, `LED`) are enforced at import, and `ci.yml`'s `source-checksum-guard`
re-validates before merge.

### FLAG-DOM-XSS — SECURE

The hyperscript helper `scripts/h.js` builds children as text nodes only
(`document.createTextNode`), exposes no raw-innerHTML prop, and ignores string `on*` handlers,
so manifest fields rendered through `h(...)` cannot inject markup. `fromHTML()` is fed only
static SVG strings. The dynamic `innerHTML` sinks in `state.js` wrap untrusted values in
`escapeHtml()` (`scripts/utils/escape-html.js`); static-string `innerHTML` assignments contain
no untrusted interpolation. URL parameters are parsed via `URLSearchParams` and mapped to a
fixed wizard-config vocabulary (`scripts/utils/url-config.js`), never written to a DOM sink. No
unsanitized manifest/sources/URL value reaches an HTML sink.

### FLAG-PAGES-SECRET — SECURE

Grep of `index.html` and `scripts/` for bearer/authorization/apikey/access_token/client_secret
found nothing. `localhost` hits are non-sensitive URL-parse bases and CLI usage strings. The
committed public keys and the `Access-Control-Allow-Origin: *` on firmware/manifest are
intentional public-distribution artifacts, not secrets.

### FLAG-CI-PWN — SECURE

`ci.yml:22-26` is `pull_request` (not `pull_request_target`) with top-level `contents: read`;
a fork PR runs `npm test` with a read-only token and no fork-available secrets.
`firmware-publish.yml` triggers on `push`/`release`/`workflow_dispatch` (write-gated);
`firmware-import.yml` and `add-firmware-source.yml` are `workflow_dispatch` only. No
`issue_comment`, `issues`, or `workflow_run` triggers.

### FLAG-CI-INJECT — SECURE

Dispatch/PR inputs are routed through `env:` and referenced as `$VAR`, with an explicit
anti-injection comment (`add-firmware-source.yml:80-103`, `firmware-import.yml:66-89`). The
`gh pr create` bodies interpolate only `github.run_id` (integer-safe) and env-bound
dispatch inputs supplied by users who already hold Actions-run permission — not an
outside-contributor vector.

### FLAG-ACTION-UNPINNED — SECURE

Every `uses:` is a full 40-char SHA pin with a version comment, all first-party `actions/*`
(`checkout@9c091bb…#v7.0.0`, `setup-node@48b55a0…#v6.4.0`, `setup-python@ece7cb0…#v6.3.0`,
`configure-pages@45bfe01…#v6.0.0`, `upload-pages-artifact@fc324d3…#v5.0.0`,
`deploy-pages@cd2ce8f…#v5.0.0`). No floating tags, no third-party actions.

### FLAG-TOKEN-SCOPE — SECURE

`ci.yml:25-26` is `contents: read`. `firmware-publish.yml:35-38` grants `contents: read`,
`pages: write`, `id-token: write`; the `id-token: write` is scoped to GitHub Pages OIDC
deploy (re-declared only on the `deploy` job, `:265-267`) — firmware signing uses the
`WEBFLASH_FIRMWARE_PRIVATE_KEY_B64` repo secret, not OIDC, so `id-token` is Pages-only.
`firmware-import.yml` and `add-firmware-source.yml` take `contents: write`
(+`pull-requests: write`) matching their commit/PR actions. No `write-all`.

## Regression note

No prior CTF baseline exists, so no SECURE→CAPTURED regression can be computed this run. All
four captures are Low and match the repo's own documented posture (test-only committed key,
deliberate signature non-enforcement, esp-web-tools SRI with acknowledged sub-chunk gap,
github-actions-only dependabot). Future re-runs should diff against this table; a move of
FLAG-MANIFEST-TRUST, FLAG-DOM-XSS, or FLAG-SOURCES-INTEGRITY toward CAPTURED-higher, or the
promotion of `dev-2026-01` to `active`, would be the regressions to watch.

## Gated remediation appendix (proposals only — nothing applied)

- FLAG-MANIFEST-TRUST — **GATED** (touches the manifest/signing trust surface). Proposal:
  enforce the Ed25519 `signature_verified` check against the `active` production key before
  enabling install, turning the existing skip into a hard gate. This is the "separate explicit
  project" the code anticipates and needs owner sign-off; do not weaken the existing SHA-256
  gate while doing so.
- FLAG-SECRET-TREE — **SAFE TO AUTOMATE** as a guard, **GATED** as a key action. The committed
  test key is intentional; no removal is proposed. Safe-to-automate: keep/strengthen the CI
  test that fails if `dev-2026-01` is ever set to `active` in `trusted-keys.json`.
- FLAG-SRI — **SAFE TO AUTOMATE**: none of these touch the hard-stop set. Options: self-host the
  Inter font to drop the un-hashed Google Fonts stylesheet, or accept it as CSP-constrained.
  esp-web-tools sub-chunk coverage would require self-hosting the pinned dist, a larger change.
- FLAG-DEP-VULN — **SAFE TO AUTOMATE**: add an `npm` ecosystem block to `.github/dependabot.yml`
  so the Jest advisories are tracked; optionally `npm audit fix` in a dev-only PR.
